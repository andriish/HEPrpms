# HEPrpms Agent Instructions

## Purpose
This file provides repository-specific guidance for AI assistants working on `HEPrpms`.

## Repository scope
- `HEPrpms` is a collection of RPM packaging recipes for High Energy Physics (HEP) software.
- The repository contains `.spec` files, patches, and build scripts for many HEP packages.
- Binary packages are built and published on COPR:
  - `https://copr.fedorainfracloud.org/coprs/averbyts/HEPrpms/`
  - `https://copr.fedorainfracloud.org/coprs/averbyts/HEPrpmsSUSE/`
- The openSUSE packages are also built in the OBS project `home:averbyts:HEPrpmsSUSE` (see the OBS section below).
- The root `README.md` documents supported distros, repository use, and build instructions.

## What to focus on
When helping with this repo, prioritize tasks around:
- RPM spec file maintenance and updates
- patch creation/fixes for package sources
- ensuring package build compatibility with Fedora, CentOS/EPEL, and openSUSE targets
- understanding package metadata, dependencies, and build requirements
- fixing packaging mistakes such as invalid macros, wrong source URLs, missing build requirements, or bad patch application
- improving documentation for package usage or build instructions

## How to work with the codebase
- Inspect package directories under the root for the relevant package version and patch files.
- Use `README.md` and the COPR repo pages as the authoritative high-level repository documentation.
- If a change touches packaging, check for related `.patch` files, `srpmsbuild.sh`, `alllocal.sh`, and `spectool` usage.
- If asked to add or change packages, prefer minimal, semantic edits rather than broad refactors.
- Consult `DEPENDENCIES.md` in the repository root to understand the dependencies between the packages in this repository (direct dependencies, reverse dependencies, build order, and the distribution packages they rely on). Use it to decide which packages must be built first and which packages are affected by a change. When a package's `BuildRequires:`/`Requires:` on another repository package changes, or a package is added, update `DEPENDENCIES.md` too.

## New version packaging workflow
When creating a spec file for a new package version, follow these steps:
- Identify the package directory and latest version subfolder under the package name.
- Copy the existing `.spec` file and any relevant `.patch` files from the current version directory as a starting point.
- Update version-related fields in the spec file: `Version:`, `Release:`, source URL(s), checksums, and any version-specific build logic.
- Preserve existing changelog history; keep the old changelog entries and append the new version note to the top of `%changelog`.
- Verify changelog entry dates are valid and use the correct weekday; RPM warns on bogus changelog dates.
- Verify the upstream source tarball or archive location and update `Source0` / `Source1` accordingly.
- Add or update patch references only if the new version still requires the same fixes; remove obsolete patches and add new ones when necessary.
- Check `BuildRequires:` and runtime `Requires:` for new or changed dependencies introduced by the new upstream release.
- Run local package tools like `spectool` or `rpmbuild -bp` if available to validate sources and syntax.
- Keep the new version directory layout consistent with the repository convention and include any package-specific build helper scripts if needed.
- Provide reasonable changelog entries explaining the version update and any packaging changes.
- Patches: if the previous version of a package needed patches (`patch-<package>-0.txt`, generated by `do.sh` from the `ORIG/` and `PATCHED/` trees), assume that the new version needs them too. Do not drop a patch because upstream restructured the files; port it instead. To do so, copy the files listed in `ORIG/` from the new upstream tarball, re-apply the old `diff -Naur ORIG PATCHED` to the new `PATCHED/` copies, resolve rejected hunks by hand (shifted context, renamed variables, new lines of the same kind), and regenerate the patch with `sh do.sh`. Also check that the patch still covers everything it has to cover: for example, new upstream modules or files of the same kind as the patched ones (such as new `fjcontrib` module Makefiles) need the same edits. Verify with `patch -pN --dry-run` on the pristine tarball.
- Major-version rules: do not bump `gosam` to 3.x, `EvtGen` to 3.x (upstream numbering `03.xx.xx`), or `njet` to 3.x. These packages stay on the 2.x series (`gosam` 2.1.x, `EvtGen` 2.x, `njet` 2.x); only update them to newer 2.x releases. Do not create new version directories, build recipes, or COPR registrations for the 3.x releases, and ignore them when `scripts/check-new-versions.sh` reports them as newer upstream versions. The existing `gosam/3.0.2` and `njet/3.1.1` directories are kept only because they are newer than the COPR versions (see the retention rules); do not build or register them.
- No uproot5: `python-uproot4` stays on the 4.x series (the upstream repository is named `uproot5`, but only its 4.x tags are used). Do not bump it to 5.x and do not package `uproot5`; `scripts/check-new-versions.sh` already restricts it to 4.x versions.
- Some upstreams only keep their newest release downloadable. For `ginac`, typically only the latest sources (https://www.ginac.de/Download.html) are available, so an older `ginac` version can usually no longer be rebuilt from its `Source0` URL. When bumping `ginac`, update the version and `Source0` together, and do not expect to be able to fetch the previous release afterwards. Check the download location before relying on an older version of any package whose upstream is a plain download page.

## Adding a new package
When adding a package that does not yet exist in the repository (for example `OpenPHIGS`):
- Create `<package>/<version>/<package>.spec`, plus any patches and a `do.sh` if patches are generated from `ORIG/` and `PATCHED/` trees.
- RPM `Version:` cannot contain `-`. If the upstream tag does, e.g. `v0.6-5`, use `Version: 0.6.5` and a `%global upstream_ver 0.6-5` macro for `Source0` and `%setup -n`. The downloaded file keeps the upstream name (`v0.6-5.tar.gz`), and that name is what `srpmsbuild.sh` stores in `rpmbuild/SOURCES`.
- Run `sh srpmsbuild.sh <package> <version>` once; it fails on an unknown checksum and writes it to `md5sums.txt.rej`. After checking the source, add the line `<md5>  <package>/<version>/rpmbuild/SOURCES/<file>` to `md5sums.txt` and rerun.
- Add a row for the package to the table in `README.md`, keeping the alphabetical order.
- Once the package is committed and pushed, register it in COPR with `scripts/copr-add-package.sh <package> <version>`.
- Add the package to `DEPENDENCIES.md` (dependency table, build-order layer, reverse dependencies, graph, and distribution dependencies). Add it to the `HEPrpms` meta package only if it is meant to be part of the full collection.
- If the build needs distribution packages that are not installed locally (such as `glew-devel`), verify the binary build in a clean chroot, e.g. `mock -r fedora-rawhide-x86_64 <package>.src.rpm`, instead of relying on `--nodeps`.
- Check whether upstream installs files relative to the prefix (for example `lib/` or `tests/`) rather than to `%{_libdir}`; relocate them in `%install` so that the package passes the unpackaged-files check.

## Local build workflow
This repository supports local package builds for verification.
- The root script `srpmsbuild.sh` is the primary local build helper.
- From the repository root, run:
  - `sh srpmsbuild.sh <package> <version> --build`
  - this downloads sources referenced by the `.spec`, checks MD5 checksums against `md5sums.txt`, executes `do.sh` if present, builds the SRPM, and then rebuilds the binary RPMs.
- Omitting `--build` creates only the SRPM.
- Build artifacts are written under `<package>/<version>/rpmbuild`, so multiple packages can be built in parallel without interfering.
- `alllocal.sh` is a wrapper that defines a `BUILDLIST` array of `package:version` entries, then runs `srpmsbuild.sh` for each item in parallel and saves logs under `logs/`.
- Local build output and failure details are stored in `logs/`, and the AI agent should read and analyze those logs when diagnosing build issues.
- Use `alllocal.sh` as a template: uncomment or add the desired `package:version` lines, then run `sh alllocal.sh` from the repo root.
- Local builds require `rpmdevtools`, `wget`, and network access to download upstream source archives.

## Scripts and COPR project maintenance
- All helper scripts for repository maintenance live in the `scripts/` directory (`srpmsbuild.sh` and `alllocal.sh` remain in the repository root because the COPR package definitions call `srpmsbuild.sh` from there).
- `scripts/copr-add-package.sh [--projects LIST] [--build] [--dry-run] <package> [<version>]` registers a package in the COPR project(s) as a custom source that clones `https://github.com/andriish/HEPrpms.git` and runs `srpmsbuild.sh <package> <version>`; if the package already exists in COPR it is updated instead. The default project is `HEPrpms`; use `--projects HEPrpms,HEPrpmsSUSE` for both. The package must be committed and pushed to GitHub before COPR can build it. It needs a valid `~/.config/copr` token; use `--dry-run` to only print the `copr-cli` commands.
- `scripts/git-rm-unused.sh [--run] [--keep NAME]` prints (or with `--run` executes) the `git rm` command that removes unused package/version directories. The COPR package list is read with `copr-cli list-packages`, and the version of each package is taken from the `srpmsbuild.sh <package> <version>` line of its COPR script.
- i686: the `HEPrpms` COPR project has the `fedora-{43,44,45,rawhide}-i386` chroots (there are no EPEL i386 chroots), but only `OpenPHIGS` and `cernlib` are built for them. Every other package has `*-i386` on its COPR chroot denylist (`--chroot-denylist`), which `scripts/copr-add-package.sh` sets (the exceptions are in its `I686_PACKAGES` variable); keep it when editing a package. Build the two i686 packages with `copr-cli build-package --nowait --name <package> -r fedora-rawhide-i386 -r fedora-45-i386 -r fedora-44-i386 -r fedora-43-i386 averbyts/HEPrpms`. `cernlib` needs `xbae-devel`, which is not built for i686.
- `scripts/check-new-versions.sh [--package NAME] [--jobs N] [-v]` lists the packages for which upstream has a newer version than the newest one built in the `HEPrpms`/`HEPrpmsSUSE` COPR projects, together with whether the repository already has a directory for it. The upstream location is derived from `Source0` (git tags for GitHub/GitLab/Bitbucket archives, the download-directory listing otherwise); packages that need another location or cannot be checked have an entry in the `OVERRIDE` table at the top of the script. Pre-release and date-like versions are ignored. Every network request is limited to 60 seconds: sites that are unreachable or that do not answer in time are unavailable, are not checked, and are listed as skipped instead of failing the run, as are sites behind the Anubis bot protection. The helper functions shared with `git-rm-unused.sh` are in `scripts/lib-copr.sh`.
- Order of COPR builds: packages that depend on each other must be built in dependency order, taken from the build-order layers in `DEPENDENCIES.md`, and the packages that depend on a rebuilt or bumped package (see the reverse dependencies there, transitively) have to be rebuilt after it. Do not poll and submit the builds one by one; let COPR schedule them. Submit everything at once with `copr-cli build-package --nowait --name <package> averbyts/HEPrpms`, grouping the packages into batches by layer: the first package of the first batch is submitted without an option, the first package of every later batch with `--after-build-id <id of the first build of the previous batch>`, and every other package of a batch with `--with-build-id <id of the first build of its own batch>`. COPR then starts a batch only after the previous one has finished, and does not build the later batches if an earlier one fails. Packages within one batch must not depend on each other. Update the COPR package definition first (`scripts/copr-add-package.sh <package> <version>`) when a package is bumped, and only submit builds after the commits are on the GitHub branch that COPR clones.
- Retention rules: a `<package>/<version>` directory stays in the repository if (1) that version is built in the `HEPrpms` or `HEPrpmsSUSE` COPR project, or (2) its version is newer than the newest version of that package built in those projects (a pending update), or (3) the package is protected, which by default is the `HEPrpms` meta package. All other directories, including packages that are not built in COPR at all, are removed. Do not delete package directories by hand; use the script, and do not add a version directory for an old version that is not built in COPR.
- Packages that were removed under these rules (`CGAL`, `DD4hep`, `imake`, `motif`, `pythia8`, `transfig`) are taken from the distribution by their dependents; see `DEPENDENCIES.md`. If one of them has to be built again, add it back with the "Adding a new package" steps and register it in COPR.
- After running `scripts/git-rm-unused.sh --run`, update `DEPENDENCIES.md` (and the table in `README.md`) for the removed packages, and review `git status` before committing.

## openSUSE Build Service (OBS)
The OBS project `home:averbyts:HEPrpmsSUSE` (`https://build.opensuse.org/project/show/home:averbyts:HEPrpmsSUSE`) mirrors the COPR project `HEPrpmsSUSE`: the same packages in the same versions, for openSUSE Tumbleweed (x86_64). Its `openSUSE_Tumbleweed` repository builds against `science/openSUSE_Tumbleweed` first and `openSUSE:Tumbleweed/standard` second (the base of `science`; the Factory snapshot lacks libraries that `science` packages need, e.g. `libcgraph.so.8` for `root6-libs`), so packages from the openSUSE `science` repository are available as build dependencies. It is managed with `osc` (credentials in `~/.config/osc/oscrc`, API `https://api.opensuse.org`); the repository scripts are not changed for it.
- Nothing is built on the local machine for OBS and no SRPMs are uploaded. OBS cannot run `srpmsbuild.sh`, so each OBS package has a `_service` file that exists only in OBS (it is not stored in this repository). It makes OBS (1) clone `https://github.com/andriish/HEPrpms.git` with `obs_scm`, extracting the files of `<package>/<version>/` (the spec file and the patches) from the git tree, and (2) run `download_files`, which downloads the `SourceN:` URLs of the spec file. Without `download_files` OBS has no sources; git sync (`scmsync`) was tried and does not help, because the package then consists only of the git files.
- Consequences: the spec file, the patches and any local source files must be committed and pushed to GitHub (the patches that `do.sh` generates from `ORIG/` and `PATCHED/` are committed for this reason, regenerate them with `sh do.sh` and commit them when `ORIG/` or `PATCHED/` change; `do.sh` and the `ORIG/`/`PATCHED/` trees are not used by OBS), and the `md5sums.txt` check is not performed.
- `scripts/obs-add-package.sh [--project NAME] [--revision REV] [--dry-run] <package> [<version>]` creates the package in the OBS project if needed, generates the `_service` file and commits it with `osc`; for an existing package whose `_service` is unchanged it only refreshes the sources from git (`osc service remoterun`). The newest version directory is used by default. Use `--dry-run` to print the `_service` file.
- `scripts/obs-sync.sh [--project NAME] [--copr OWNER/PROJ] [--jobs N] [--skip-existing] [--dry-run] [<package> ...]` creates the OBS project (with the repository described above) if it does not exist and sets up the given packages, or all packages of the COPR project `averbyts/HEPrpmsSUSE`, in the versions that COPR builds, by calling `obs-add-package.sh`. Failed packages are listed at the end, logs are in `logs/obs-add-<package>.log`.
- OBS builds a package automatically after a commit; to rebuild use `osc rebuild home:averbyts:HEPrpmsSUSE <package>`, to look at the state `osc results home:averbyts:HEPrpmsSUSE <package>` and the build log `osc api /build/home:averbyts:HEPrpmsSUSE/openSUSE_Tumbleweed/x86_64/<package>/_log`. Packages that depend on each other are scheduled by OBS itself, no batches are needed.
- OBS is stricter than COPR: for example it fails the build when a package leaves a directory unowned (`directories not owned by a package`); own the directory in `%files` (`%{_libdir}/Dir`, not `%{_libdir}/Dir/*`) instead of ignoring the error.
- Package layout: the split of the files into (sub)packages on openSUSE must stay close to the RHEL/Fedora case. Use the same subpackage names and the same contents, and a package must provide and require the same things in both cases, so that users and the packages that depend on them (see `DEPENDENCIES.md`) are not affected by the distribution. Distribution differences go into `%if 0%{?suse_version}` blocks (library subpackage naming that SUSE policy requires, `ldconfig` scriptlets, undefined macros like `python3_pkgversion`, `_lto_cflags`, and so on), not into a different file split; fix the errors that OBS reports (unowned directories, rpmlint errors with a high badness) with the smallest change that keeps the layout, and do not change the Fedora/EPEL output of a spec file when fixing an openSUSE problem.
- Known problems that are not handled yet: sources from HepForge `downloader?f=...` URLs (whizard, Herwig, golem95, collier, applgrid, blackhat, recola, tmdlib, HJets) have no file name for `download_files`, `qgraf` has a source tarball that `do.sh` creates from the `.f08` file, and sites that block the OBS downloader (HepForge, CERN GitLab) may need another source location.

## Best practices
- Keep changes aligned with RPM packaging conventions used in this repository.
- Do not assume an external build system beyond COPR; the repo is primarily about packaging recipes.
- Mention the supported platforms and the COPR build service when relevant.
- If a task requires a missing detail, ask for the target distro/version or the specific package name.

## Non-goals
- Do not invent new package build platforms that are not documented here.
- Do not make broad source code changes unrelated to RPM packaging.
- Do not assume there is a full application source tree for every package; many directories contain only packaging metadata.
